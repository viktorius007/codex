## Proven finding

**HTTP SSE overwrites a terminal quota failure with a later transport failure.** `process_responses_event` classifies `response.failed` with `insufficient_quota` as `ApiError::QuotaExceeded` (`sse/responses.rs:417-428`). The SSE loop stores this error (`:681-688`) but replaces it with `ApiError::Stream` if the next byte read fails or the idle timer expires (`:596-614`). WebSocket handling returns the classified error immediately (`endpoint/responses_websocket.rs:851-860`). Core treats quota as terminal and stream errors as retryable (`protocol/src/error.rs:379-425`), so the HTTP case can resubmit a refused request. The test `failed_response_keeps_terminal_classification_when_transport_fails_afterward` supplies a failed quota event followed by a network error and expects the original quota classification. It compiled and failed twice on unchanged production: `Some(Err(Stream("Transport error: network error: transport failed after terminal response")))` was received instead of `Some(Err(ApiError::QuotaExceeded))`. The official [Responses streaming event reference](https://developers.openai.com/api/reference/resources/responses/streaming-events) identifies `response.failed` as the failed response event; [OpenAI Agents SDK terminal state guidance](https://openai.github.io/openai-agents-js/guides/models/#responses-terminal-states) treats it as a terminal failure. The source supports a similar overwrite by idle timeout, though this test specifically proves the later network-error path. Full patch and structured trace are in `findings.json`.

## Investigated but not admitted

**Partial usage in a completed event.** `ResponseCompletedUsage` requires `cached_tokens` whenever `input_tokens_details` is present (`sse/responses.rs:118-166`). A fixture omitting that field made the whole `response.completed` parse fail as `ApiError::Stream` (`:490-513`), which is retryable. The temporary test `completed_response_with_partial_usage_does_not_request_a_new_generation` compiled and failed with `missing field cached_tokens`; raw log and original test patch are preserved in `retry-red.txt` and `initial-probes.patch`. This fixture violates the official [Response usage schema](https://developers.openai.com/api/reference/python/__sdk_schema?declaration=%28resource%29+responses+%3E+%28model%29+response+%3E+%28schema%29+%3E+%28property%29+usage&selected=%28resource%29+responses+%3E+%28method%29+retrieve), which requires `cached_tokens` within `input_tokens_details`. It may be a compatibility problem for configured proxies, but no supported-provider contract or real instance establishes that path here. GitHub [#37141](https://github.com/openai/codex/issues/37141) is a lead. The test was removed from the replay patch and no finding was admitted.

## Checked alternatives and limits

- Missing or null whole `usage` is accepted as `token_usage: None` by `ResponseCompleted` (`sse/responses.rs:118-125,490-506`), and the existing parser test at `:847-910` checks this. This does not establish complete cost accounting when upstream sends no usage.
- `response.incomplete` maps to a stream error (`sse/responses.rs:479-489`). The provider reference describes it as a finished incomplete response, but WebSocket steering can deliberately produce an incomplete event followed by a successor response. Without a controlled end-to-end steering sequence and an approved replay policy, [#38831](https://github.com/openai/codex/issues/38831) remains a lead; no defect is reported from source alone.
- Output items may have been emitted before a terminal parse error (`sse/responses.rs:353-365`, `core/src/session/turn.rs:2635-2884`). This audit does not claim side-effect or duplicate-tool behavior; the separate ordering slice owns batch assembly and tool execution.
- No private-session data or live provider was used. No production code was edited. The proven test asserts the terminal quota error after exact stream events; it does not measure how many retries a complete Codex turn would make.

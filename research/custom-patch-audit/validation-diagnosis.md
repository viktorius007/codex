# Core validation failure diagnosis

Source checkout: `a0cd462856168f4dbc430a6ee94f5fcd771808a6` plus the uncommitted local.7 fixes. This is a read-only diagnosis; no production or test source was changed.

## Reproduction

- Full `just test -p codex-core` log: `/private/tmp/codex-patch-audit/root-core-tests.log`, 4,599 passed, 10 failed, 27 skipped. All ten failures repeated on nextest's retry.
- Outside the outer Seatbelt sandbox, with `env -u CODEX_SANDBOX RUSTC_WRAPPER= HOST_CC=clang HOST_CXX=clang++`, the three-case focused `just test -p codex-core -E ...` run gave 2 passed (credential `filtered_global_startup`, MCP runtime refresh) and 1 failed (denied-read zsh fork approval).
- The four-case focused run with `--test-threads=2` gave 2 passed (credential `login_startup`, MCP zero-grace startup timeout) and 2 failed (skill script and persistent-terminal Guardian). The latter two failed again on retry.
- A seven-case credential-broker run with `--test-threads=2` passed all seven variants in 9.177 seconds, including all five that failed in the full suite. This supports a suite-load timing cause for those five; it does not prove the precise source of contention.

## Findings and safe validation corrections

1. **Five credential-broker failures: load-sensitive event waits, no reproduced behavior failure.** The full suite ended each at `core/tests/common/lib.rs:388` after the helper's ten-second minimum event wait. Each variant completes in about three seconds with two test threads. Keep the full-suite red result visible, and use the bounded-concurrency seven-case rerun as targeted validation. If a full-suite green gate is required, rerun with bounded nextest concurrency and investigate contention if these still fail. Do not raise a timeout without measured isolated and loaded timings. The test sets `yield_time_ms: 10_000` at `core/tests/suite/approvals.rs:2952,2959` and then waits for completion at `:3015`.
2. **Two optional-MCP failures: load-sensitive fixture deadlines.** The full suite expired at `mcp_optional_startup_grace.rs:229-234` (500 ms initial turn deadline) and `:93-99` (five-second wait for initialization to begin). Both passed focused reruns outside the outer sandbox. The server readiness checks use `yield_now` and fixed wall-clock deadlines while the full suite runs thousands of tests. The safe correction is bounded-concurrency validation; if a stable full-suite test is needed, synchronize on the fixture's readiness/response events and assert the catalog outcome rather than simply increasing arbitrary deadlines. No production defect is established by these two failures.
3. **Skill-script test: deterministic double-consumption of `TurnComplete`.** `wait_for_exec_approval_request` returns `None` only after it consumes `EventMsg::TurnComplete` (`skill_approval.rs:119-125`). The test then calls `wait_for_turn_complete` (`:207-213`), waiting for a second completion that never comes; both full and isolated retries time out at `common/lib.rs:388`. Exact test correction: remove the second wait and inspect the mounted completion response immediately after the `None` assertion. That keeps the intended no-approval and sandbox assertions.
4. **Denied-read zsh-fork test: the child command requests a separate approval.** After the parent approval (`unified_exec_zsh_fork_approvals.rs:98-105`), `wait_for_completion_without_approval` panics on an intercepted `["/bin/cat", ".../secret.env"]` approval at `:971`, in both full and isolated runs. This is distinct from an unauthorized read: the test stops before approving the child, and the log does not show the secret disclosed. The fixture should explicitly handle the child approval (deny it, then assert the secret remains unread) if the intended invariant is that parent approval does not authorize denied reads. If the intended invariant instead forbids *even requesting* a child approval, this requires a separate product-policy decision; the current test evidence alone cannot choose that rule.
5. **Persistent-terminal Guardian test: its second turn violates the denied-read retention guard.** The test changes both CWD and denied path at `unified_exec_zsh_fork_approvals.rs:559-575`. `TerminalPermissions::review_requirement` rejects a running terminal when current denied-read filesystem context differs from its launch context (`stdin_approval.rs:117-127`), because approval cannot retrofit restrictions. Parsing the original full-suite wiremock request shows `write_stdin` returned `write_stdin rejected: this terminal cannot enforce the current denied-read restrictions; start a new terminal`; only four of six mocked model calls occurred, so Guardian was never reached. Exact fixture correction: keep the same filesystem context (including CWD and denied-read entry) across turns while changing the reviewer, or create a separate test for policy drift that asserts this rejection. The current fixture cannot simultaneously change denied-read context and expect the persistent terminal's Guardian path.

The three deterministic failures occur before the local `write_stdin` exit-wake disarming path can explain them: the skill test double-waits, the denied-read test stops at a child approval, and the persistent-terminal test is rejected at policy review. This does not claim an exhaustive impact analysis of the local changes.
